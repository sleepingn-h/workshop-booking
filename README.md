## 기술 스택과 선택 이유

Next.js 16 App Router·React 19·TypeScript strict mode를 사용합니다. UI는 Tailwind CSS 4·shadcn/ui·Lucide, 자동 테스트는 Vitest·React Testing Library(jsdom)로 구성했습니다.

| 결정 | 선택과 이유 |
| --- | --- |
| ADR-001 · Next.js App Router | 고객·운영자 화면과 REST API를 한 프로젝트에서 제공합니다. 공개 목록·상세는 서버 렌더링으로 검색 노출과 공유 미리보기를 지원합니다. |
| ADR-002 · 순수 규칙과 처리 순서 | `rules.ts`는 규칙, `db.ts`는 조회 → 검증 → 저장을 담당합니다. 서버 컴포넌트도 `db.ts`를 직접 호출해 HTTP 왕복을 줄입니다. |
| ADR-003 · Supabase | Postgres·Storage를 사용하고 테이블·함수·버킷·샘플을 SQL 파일 하나로 준비합니다. Postgres 함수의 트랜잭션과 행 잠금으로 정원을 보장합니다. |
| ADR-004 · 테스트 먼저 작성 | 구현 파일 옆에 테스트를 두고 가드로 작성 순서를 확인합니다. 규칙은 순수 함수로, 외부 호출은 모킹으로 검증하고 실제 DB 동작은 배포 환경에서 시연합니다. |
| ADR-005 · 요청 시각 전달 | 요청마다 한 번 읽은 시각을 규칙과 SQL 함수에 함께 전달합니다. 시간 경계를 고정 시각으로 테스트할 수 있습니다. |
| ADR-006 · HMAC 서명 쿠키 | 단일 운영자는 비밀번호로 로그인하고 12시간 유효한 httpOnly 쿠키로 인증합니다. 별도 세션 저장소와 사용자 테이블을 두지 않습니다. |
| ADR-007 · TanStack Query | 예약 조회·운영자 화면의 조회·변경·관련 쿼리 무효화를 관리합니다. 서버 상세의 회차·남은 자리는 `router.refresh()`로 갱신합니다. |
| ADR-008 · 수동 승인 | 승인 대기도 자리를 차지해 승인 시 정원이 초과되지 않습니다. 운영자가 처리하며 자동 만료는 없습니다. |
| ADR-009 · 비회원 예약 조회 | 예약번호와 전화번호 뒷자리 4자리로 조회·취소합니다. 일회성 예약에 고객 계정이 필요하지 않습니다. |
| ADR-010 · SQL 재실행으로 초기화 | 샘플을 다시 준비하는 절차를 SQL 파일 하나로 유지합니다. 시연 직전에 직접 초기화하며 정기 초기화나 조회 시 일정 보정은 하지 않습니다. |
| ADR-011 · 운영자 API로 이미지 업로드 | 운영자 인증과 형식·크기 검증 후 서버에서 Storage에 저장합니다. 브라우저는 자체 REST API만 호출합니다. |

각 결정의 트레이드오프는 [ADR](docs/ADR.md), 처리 구조와 상태 갱신은 [아키텍처](docs/ARCHITECTURE.md)에 정리했습니다.

## 구현 범위와 후속 범위

MVP 구현 범위:

- 공개 클래스 목록·상세, 회차별 남은 자리·마감 안내, 검색 노출·공유 미리보기
- 회차·1~4명 인원·예약자 정보로 신청, 예약번호 확인·복사, 조회·기한 내 취소
- 운영자 로그인·로그아웃, 회차·상태 필터와 이름·전체 전화번호 검색, 승인·거절·취소
- 클래스 생성·수정·삭제·공개 전환(예정 회차가 없으면 공개 대신 회차 추가 안내), 대표 이미지 업로드·교체
- 회차 생성·정원·시각 수정·삭제·취소, 예약 이력 보호와 활성 예약 일괄 취소
- Supabase 예약 저장, 샘플 데이터, 모바일~데스크톱 화면과 입력·제출·실패·확인 상태 처리

MVP 제외 사항:

- 고객 회원가입·로그인
- 서비스 내 결제·환불
- 자동 문자·이메일 알림
- 승인 대기 예약의 자동 만료
- 고객의 예약 내용 직접 수정: 취소 가능한 기한에 취소 후 재신청

후속 범위는 실제 DB 연동·동시 신청(R-15)의 자동 검증입니다. 현재 자동 테스트는 실제 DB에 접속하지 않습니다. 정원 보장은 Postgres 함수의 행 잠금으로 구현했으며 배포 환경 시연으로 확인합니다. 정원 변경 경합, 회차 취소의 전체 반영, 삭제·시각 변경의 이력 보호에 대한 DB 연동 자동 검증도 후속 범위입니다.

기능 개요는 [PRD](docs/PRD.md)에 정리했습니다.

## 핵심 정책과 규칙 ID

테스트 이름의 `R-xx`는 아래 정책에 대응합니다. 신청·승인·고객 취소의 시간 제한은 서버가 업무 요청 처리를 시작할 때 한 번 읽은 요청 시각으로 판정하고, 상태·남은 자리는 저장 시점에 다시 확인합니다. 화면의 일정과 취소 기한은 항상 한국 시각(`Asia/Seoul`)으로 표시합니다.

| 내부 상태 | 표시명 |
| --- | --- |
| `pending` | 승인 대기 |
| `confirmed` | 참여 확정 |
| `rejected` | 거절됨 |
| `cancelled` | 취소됨 |

| 규칙 ID | 정책 요약 |
| --- | --- |
| R-01 | 차지된 자리는 승인 대기·참여 확정 예약 인원의 합입니다. |
| R-02 | 남은 자리는 정원에서 차지된 자리를 뺀 값입니다. |
| R-03 | 거절·취소 예약은 자리를 차지하지 않으며 해당 인원만큼 자리가 복구됩니다. |
| R-10 | 신청 성공 시 승인 대기 상태와 고객용 예약번호를 발급합니다. |
| R-11 | 신청 인원이 남은 자리보다 많으면 신청할 수 없습니다. |
| R-12 | 한 예약의 인원은 1~4명의 정수입니다. |
| R-13 | 취소된 회차에는 신청할 수 없습니다. |
| R-14 | 요청 시각이 회차 시작 시각 이상이면 신청할 수 없습니다. |
| R-15 | 동시 신청과 정원 변경이 경합해도 차지된 자리는 정원을 넘지 않습니다. |
| R-16 | 같은 회차·전화번호의 승인 대기·참여 확정 예약이 있으면 추가 신청할 수 없습니다. 공백·하이픈은 제거하며 거절·취소 후 재신청할 수 있습니다. |
| R-17 | 시작 전 승인·거절하며 자동 만료는 없습니다. 시작 후 미처리 건은 운영자가 거절·취소로 정리합니다. |
| R-18 | 고객은 예약 정보를 직접 수정할 수 없습니다. 기한 내 취소 후 재신청하며 기존 자리는 보장되지 않습니다. |
| R-19 | 예약번호 분실 시 공방에 문의하며 운영자가 이름·전체 전화번호로 검색해 안내합니다. |
| R-20 | 승인 대기 → 참여 확정·거절됨·취소됨, 참여 확정 → 취소됨만 허용하며 처리 주체와 기한을 검사합니다. |
| R-21 | 거절·취소는 되돌릴 수 없는 최종 상태입니다. |
| R-22 | 요청 시각이 회차 시작 시각 이상이면 승인할 수 없습니다. |
| R-30 | 예약번호·전화번호 뒷자리 4자리가 모두 일치해야 조회·취소할 수 있으며 틀린 항목을 구분하지 않습니다. |
| R-31 | 승인 대기는 시작 전까지, 참여 확정은 시작 24시간 전 정각까지 고객이 취소할 수 있습니다. 거절·취소 상태는 다시 취소할 수 없습니다. |
| R-32 | 운영자는 승인 대기·참여 확정 예약을 시간 제한 없이 취소할 수 있습니다. |
| R-33 | 고객은 조회 화면에서 상태와 신청자(일부 가림)·일시·장소·인원(예상 비용)·결제 방법·문의처를 직접 확인합니다. 시작 후 승인 대기는 참여 미확정·공방 문의를 안내합니다. |
| R-40 | 정원을 차지된 자리보다 적게 줄일 수 없습니다. |
| R-41 | 상태와 관계없이 예약 이력이 있는 회차는 삭제할 수 없으며 운영 중단은 회차 취소로 처리합니다. |
| R-42 | 회차 취소 시 승인 대기·참여 확정 예약을 함께 취소하며 거절·취소 이력과 고객 조회를 유지합니다. |
| R-43 | 예약 이력이 전혀 없는 회차는 삭제할 수 있습니다. |
| R-44 | 예약 이력이 있으면 시작 시각을 바꿀 수 없습니다. 이력이 없으면 미래 시각으로 변경하고, 이력이 있는 일정 변경은 취소·새 회차 생성으로 처리합니다. |
| R-45 | 취소된 회차는 다시 열 수 없으며 새 회차를 만들어야 합니다. |
| R-46 | 회차는 미래 시작 시각과 1 이상의 정수 정원으로 생성하며 소속 클래스는 바꿀 수 없습니다. |
| R-50 | 회차가 없는 클래스는 삭제할 수 있습니다. |
| R-51 | 회차가 있는 클래스는 삭제할 수 없으며 삭제 요청이 자동 비공개로 바뀌지 않습니다. |
| R-52 | 비공개 클래스는 고객 목록·상세·신규 신청에서 제외합니다. 기존 예약 조회·기한 내 취소와 운영자 관리는 유지합니다. |
| R-53 | 클래스는 장소·소요 시간(1~1440분)·비용(0~10,000,000원)·결제 방법·준비물·문의처를 모두 입력해야 생성·수정할 수 있습니다. 소개는 선택 입력입니다. |
| R-54 | 고객 상세에는 시작 전·미취소 회차만 표시합니다. 만석은 마감으로 신청을 막고, 숨겨진 회차의 기존 예약 조회는 유지합니다. 표시할 회차가 없는 클래스는 R-59에 따라 고객에게 보이지 않습니다. |
| R-55 | 공개 목록·상세는 검색 노출을 지원하며 상세 공유 시 이름·소개 요약(소개가 없으면 장소·소요 시간·비용)·대표 이미지를 제공합니다. |
| R-56 | 비공개 클래스는 검색·공유 미리보기에서 제외하고 완료·조회·운영자 화면은 noindex입니다. 신청 폼이 있는 공개 상세는 검색 노출 대상입니다. |
| R-57 | 새 클래스는 비공개로 생성하고 안내 항목·이미지·회차를 확인한 뒤 공개합니다. |
| R-58 | 클래스 이름·안내 항목 수정은 기존 예약 조회에도 반영하며 자동 알림은 보내지 않습니다. 준비물·소개·이미지는 클래스 상세에서 확인합니다. |
| R-59 | 예정 회차(시작 전·미취소, 만석 포함)가 있어야 공개할 수 있습니다. 공개 후 예정 회차가 없어지면 공개 설정은 유지한 채 고객 목록·상세에서 숨기고, 회차를 추가하면 다시 보입니다. 기존 예약 조회·취소는 유지합니다. |

## 로컬 실행

로컬 검증 환경은 Node.js **22.14.0**, npm **10.9.2**입니다.

```bash
npm install
cp .env.example .env.local
```

`.env.local`에 아래 환경 변수를 설정하고, 아래 DB 준비 절차를 마친 뒤 실행합니다.

```bash
npm run dev
```

개발 서버는 `http://localhost:3000`에서 확인합니다. 검증 명령은 다음과 같습니다. 프로덕션 빌드에는 TypeScript 검사도 포함됩니다.

```bash
npm run test
npm run lint
npm run build
```

## 환경 변수

값은 로컬의 `.env.local`과 배포 환경에 설정합니다. 서버 전용 키·비밀번호·서명 키는 브라우저에 노출하지 않습니다.

| 이름 | 용도 |
| --- | --- |
| `SUPABASE_URL` | Supabase 프로젝트 주소 |
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용 Supabase 서비스 역할 키: DB·Storage 접근 |
| `ADMIN_PASSWORD` | 운영자 로그인 비밀번호 |
| `ADMIN_SESSION_SECRET` | 운영자 세션 쿠키의 HMAC 서명 키 |
| `NEXT_PUBLIC_SITE_URL` | OG·canonical 절대 주소 생성 |
| `MOCK_DB` | `1`이면 개발 서버에서 읽기 전용 목 데이터 모드 사용 (production에서는 무시) |

### Supabase 없이 화면 확인하기

`.env.local`에 `MOCK_DB=1`과 `ADMIN_PASSWORD`·`ADMIN_SESSION_SECRET`만 설정하고 `npm run dev`를 실행하면, 아래 샘플 데이터와 같은 클래스·회차·예약으로 고객·운영자 화면을 조회할 수 있습니다. 샘플 회차 시각은 개발 서버 시작 시각 기준입니다. 신청·취소·승인과 클래스·회차 관리 같은 변경은 `MOCK_READ_ONLY` 오류로 거부합니다. 프로덕션 빌드(`npm run build && npm start`)에서는 켜지지 않습니다(ADR-012).

## DB 준비와 데모 초기화

1. Supabase 프로젝트를 생성합니다.
2. 프로젝트의 SQL Editor에서 [supabase/schema.sql](supabase/schema.sql) **전체**를 실행합니다. 테이블·예약/관리 함수·`session_stats` 뷰·`class-images` 공개 버킷·샘플 데이터를 준비합니다.
3. 샘플 이미지 `public/samples/class-1.jpg`~`class-4.jpg`(순서대로 도자기·가죽·꽃다발·캔들)는 저장소에 포함되어 있어 따로 준비하지 않습니다. 출처는 [샘플 이미지 출처](#샘플-이미지-출처)에 있습니다.
4. 데모 초기화가 필요하면 같은 SQL 파일 전체를 SQL Editor에서 다시 실행합니다.

**주의: 다시 실행하면 시연 중 만든 예약·클래스·회차를 포함한 기존 DB 데이터를 모두 지우고 다시 만듭니다.** 업로드한 Storage 파일은 초기화 후에도 남습니다.

샘플 회차 시각은 SQL 실행 시점 기준(`now() + interval`)으로 계산합니다. 지원서 제출 등 시연 직전에 직접 실행해야 합니다. 시간이 지나면 시연 회차가 이미 시작했거나 방문자 조작으로 예약·남은 자리 등이 달라질 수 있습니다. 정기 자동 초기화나 서버 시작·고객 조회 시 일정 보정은 없습니다(ADR-010).

## 시연 순서

1. 고객 화면에서 시작까지 24시간보다 많이 남고 최소 2자리가 남은 회차를 확인해 **2명**으로 신청합니다. 초기화 직후 A 도자기의 4일 후 회차는 4자리가 남아 있습니다. 기존 활성 예약과 다른 전화번호를 사용합니다.
2. 신청 완료 화면에서 승인 대기 안내와 예약번호를 확인·복사합니다. 클래스 상세를 다시 열어 남은 자리가 2명 줄었는지 확인합니다.
3. 다른 브라우저 또는 시크릿 창에서 `/admin/login`으로 로그인합니다. 회차·상태 필터로 해당 예약을 찾아 승인합니다.
4. 고객이 `/bookings/lookup`에서 예약번호·전화번호 뒷자리로 재조회해 참여 확정을 확인합니다. 상세를 다시 조회했을 때 남은 자리는 승인 전과 같아야 합니다.
5. 고객이 확인 절차를 거쳐 예약을 취소합니다. 취소됨 상태와 2명분 자리 복구를 확인합니다.
6. A 도자기의 만석 회차 신청 제한과 `BK-DEMO04`의 시작 24시간 이내 확정 예약 취소 제한·공방 문의 안내를 확인합니다.
7. 운영자가 회차를 추가해 고객 상세에 표시되는지 확인합니다. 이어 예약이 있는 회차를 취소하고 활성 예약이 취소됨으로 바뀌는지, 기존 예약을 고객이 계속 조회할 수 있는지, 회차가 고객 상세에서 사라지는지 확인합니다.
8. 운영자가 회차가 없는 C 꽃다발의 공개 스위치를 켜면 공개 대신 회차 추가 안내가 뜨는지 확인합니다. [회차 추가하기]로 회차를 추가한 뒤 공개하고, 고객 목록에 C가 보이는지 확인합니다.

## 테스트

자동 테스트는 Vitest·React Testing Library(jsdom)를 사용합니다. 규칙을 검증하는 테스트 이름에는 위 표의 규칙 ID를 포함하고, 시간 경계에는 고정 시각을 전달합니다.

| 대상 | 자동 검증 범위 |
| --- | --- |
| `src/lib/rules.ts` | 자리 계산·신청·상태 전이·취소 기한 경계·입력 정규화·클래스/회차 관리·이미지 검증 |
| `src/lib/auth.ts` | 비밀번호 비교·쿠키 서명·만료·변조·빈 값 거부 |
| `src/lib/db.ts` | Supabase 모킹: 단일 요청 시각 전달·입력 오류 시 DB 미호출·오류 변환·고객 인증·Storage 정리 |
| `src/lib/api.ts`, `src/lib/http.ts` | fetch 응답·네트워크 오류, JSON 파싱·인증·에러의 HTTP 응답 변환 |
| `src/app/api/**/route.ts` | db 함수 모킹: 요청 파싱·HTTP 상태·운영자 401·허용하지 않는 예약 동작 404 |
| `src/components/*.tsx` | 필드 오류·제출 중 비활성·실패 시 입력 유지·만석 시 상세 갱신·취소/삭제 확인·상태 텍스트·검색 |
| `src/lib/format.ts`, QueryProvider | 한국 시각 표시·입력 변환, 쿼리 제공자 동작 |
| `src/proxy.ts` | 쿠키 없음·무효 시 로그인 이동, 유효 쿠키 통과·로그인 경로 제외 |

- 동시 신청의 정원 유지(R-15), 전화번호 정규화·중복 차단, 거절·취소 후 자리 복구

- 회차 취소 시 활성 예약 전체 취소, 예정 회차가 없는 클래스의 공개 거부, 정원 변경·공개 전환과 신청의 경합, 삭제·시각 변경의 이력 보호

## 디렉토리 구조

```text
src/
├── app/
│   ├── (site)/         # 고객 목록·상세·신청 완료·예약 조회
│   ├── admin/          # 운영자 로그인·예약·클래스·회차 관리
│   └── api/            # 공개 예약 API·운영자 API
├── components/         # 고객·운영자 UI와 같은 폴더의 테스트
│   └── ui/             # CLI로 추가한 shadcn/ui
├── lib/                # 순수 규칙·DB 처리·인증·HTTP·시각 표시
└── proxy.ts            # 운영자 페이지 접근 보호
supabase/schema.sql     # 테이블·함수·버킷·샘플 데이터
public/samples/         # 저장소에 포함한 고정 샘플 이미지
scripts/hooks/          # TDD·위험 명령·종료 전 검증 가드
docs/                   # 공개 기획·설계·UI 문서
phases/                 # 단계별 작업 상태·산출물 요약
```

import alias `@/*`는 `./src/*`를 가리킵니다. 브라우저는 자체 REST API를 호출하고 서버 컴포넌트는 `src/lib/db.ts`를 직접 호출합니다. 상세 구조·데이터 흐름·상태 관리·테스트 책임은 [아키텍처](docs/ARCHITECTURE.md)를 참고하세요.
