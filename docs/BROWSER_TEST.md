# 브라우저 테스트 시나리오

브라우저로 고객·운영자 화면을 직접 조작해 확인하는 시나리오다. 브라우저 테스트를 할 때마다 이 문서를 기준으로 진행하고, 결과는 마지막 절의 양식으로 남긴다. 단위·컴포넌트 테스트(`npm run test`)가 다루지 못하는 화면 흐름, 저장 후 다시 조회한 결과, 반응형 배치를 확인하는 것이 목적이다.

도구는 [dev-browser](https://github.com/sawyerhood/dev-browser)를 사용한다. 사용법은 `dev-browser --help`에 있고, 스크립트는 `dev-browser --headless <<'EOF' ... EOF`처럼 표준입력으로 넘긴다.

## 1. 실행 모드

모든 시나리오는 두 모드에서 각각 실행한다. 시나리오마다 모드별 기대 결과가 다를 수 있으며, 표의 **A**·**B** 열에 적혀 있다.

| 모드 | 설정 | 확인 범위 |
|---|---|---|
| **A · 목 데이터** | `.env.local`에 `MOCK_DB=1`, `npm run dev` | 조회 화면 전체. 변경 요청(신청·취소·승인·거절, 클래스·회차 관리)은 `MOCK_READ_ONLY` 오류("목 데이터 모드에서는 변경할 수 없습니다.")로 거부되고, 입력이 유지되는지 확인한다. |
| **B · Supabase** | `MOCK_DB`를 지우거나 `1`이 아닌 값으로 두고 `npm run dev` | 전체 시나리오. 변경 결과가 저장되고 새로고침·다시 조회한 뒤에도 유지되는지 확인한다. |

### 모드 B 주의

- 테스트 예약·클래스·회차가 연결된 Supabase DB에 실제로 저장된다. 배포 데모와 같은 DB이면 테스트가 끝난 뒤 반드시 데모를 초기화한다.
- 시작 전에 `supabase/schema.sql` 전체를 SQL Editor에서 다시 실행해 샘플 데이터를 초기 상태로 맞춘다. 실행하면 기존 DB 데이터가 모두 지워진다. 업로드한 Storage 파일은 남는다.
- 시나리오가 앞 시나리오의 결과에 영향을 받으므로 **3절의 순서대로** 실행한다.

### 공통 준비

- 운영자 비밀번호는 `.env.local`의 `ADMIN_PASSWORD` 값을 쓴다. 이 문서와 테스트 기록에는 비밀번호를 적지 않는다.
- 화면 폭은 모바일 **360px**, 데스크톱 **1280px** 두 가지를 쓴다. 따로 정하지 않은 시나리오는 1280px로 진행한다.
- 시각은 모두 한국 시각(Asia/Seoul)으로 표시되어야 한다.
- 서버 오류는 화면 아래 토스트로 3~4초 동안 보인 뒤 사라진다. 확인 창 안에서 난 오류는 창을 닫지 않고 그대로 둔다. 오류 문구는 동작 직후 바로 확인한다.
- 샘플 이미지 `public/samples/class-1.jpg`~`class-4.jpg`는 저장소에 포함되어 있다. 목록·상세·운영자 화면에서 이미지가 깨져 보이면 결함으로 기록한다.

### dev-browser 메모

- 회차 라디오는 화면에서 숨긴(`sr-only`) input이라 바로 클릭되지 않는다. 회차 날짜 문구가 든 `label`을 클릭한다.
- 확인 창에는 이름이 "닫기"인 아이콘 버튼이 마지막에 있다. 확정 버튼은 순서가 아니라 이름(예: "회차 취소하기")으로 찾는다.
- 스크립트 샌드박스는 파일 경로를 읽지 못한다. 이미지 업로드는 `setInputFiles({ name, mimeType, buffer: Buffer.from(...) })`로 메모리의 데이터를 넘긴다.
- 운영자 비밀번호는 셸에서 `.env.local`을 읽어 heredoc 변수로 넘기고, 출력하지 않는다.
- 기본 스크립트 제한 시간은 30초다. 여러 절차를 한 번에 돌릴 때는 `--timeout 120`처럼 늘린다.
- 샘플 회차 시각은 모드 A에서는 개발 서버 시작 시각, 모드 B에서는 SQL 실행 시각을 기준으로 계산된다. 오래 켜 둔 서버나 오래전에 초기화한 DB에서는 "20시간 후" 회차가 이미 시작했을 수 있으니, 시작 전에 서버를 재시작하거나 DB를 초기화한다.

## 2. 사용하는 샘플 데이터

두 모드의 샘플 데이터는 같다. 전화번호 뒷자리는 앞자리 0을 포함한 네 자리로 입력한다.

| 대상 | 내용 | 쓰는 시나리오 |
|---|---|---|
| A 손으로 빚는 도자기 컵 · 4일 후 회차 | 정원 6, 차지 2(BK-DEMO01), 남은 자리 4 | BT-02, BT-03, BT-10 |
| A 도자기 · 5일 후 회차 | 정원 4, 만석(BK-DEMO02 승인 대기, BK-DEMO03 확정) | BT-05 |
| A 도자기 · 20시간 후 회차 | BK-DEMO04 확정 1명 | BT-07 |
| A 도자기 · 2시간 전 시작한 회차 | BK-DEMO05 승인 대기 | BT-08 |
| A 도자기 · 6일 후 취소된 회차 | BK-DEMO06 거절됨, BK-DEMO07 취소됨 | BT-09 |
| B 나만의 가죽 카드 지갑 · 7일 후 회차 | 정원 6, BK-DEMO10 승인 대기, BK-DEMO08 거절됨, BK-DEMO09 취소됨 | BT-11, BT-12 |
| C 작은 꽃다발 만들기 (비공개) | 회차 없음. 예정 회차가 없어 공개할 수 없다 | BT-01, BT-14 |
| D 향을 고르는 캔들 클래스 (비공개) | 6일 후 회차, BK-DEMO11 승인 대기 | BT-01, BT-09, BT-14 |
| E~N 목록용 공개 클래스 10개 | 9~32일 뒤 정각 회차 2개씩, 예약 없음. 일부는 이미지 없음(아이콘 표시) | BT-01 |

테스트에서 새로 신청할 때는 샘플과 겹치지 않는 가상 번호 `010-1234-5678`(뒷자리 `5678`)을 쓴다.

## 3. 시나리오

규칙 ID(`R-xx`)는 README의 정책 요약 표와 같다. **A** 열이 비어 있으면 모드 A의 기대 결과가 **B**와 같다.

### 고객

#### BT-01 · 클래스 목록과 비공개 클래스 (R-52, R-56, R-59)

| 절차 | B 기대 결과 | A 기대 결과 |
|---|---|---|
| 1. `/`에 접속한다. | A·B가 맨 앞에, 이어서 E~N 10개 클래스가 이미지·이름과 장소·소요 시간·비용(항목마다 한 줄)으로 보인다(A는 `120분`·`₩45,000`, B는 `150분`·`₩55,000`, N 라탄은 `무료`). 이미지가 없는 클래스는 연한 단색 면에 아이콘이 보인다. 소개·다음 회차·남은 자리는 없다. 비공개 C 꽃다발·D 캔들 클래스는 없다. | |
| 2. D 클래스 상세 주소 `/classes/10000000-0000-4000-8000-000000000004`에 직접 접속한다. | 404 상태로 "클래스를 찾을 수 없습니다" 화면이 나오고, 클래스 목록과 예약 조회로 가는 링크가 있다. | |
| 3. C 클래스 상세 주소 `/classes/10000000-0000-4000-8000-000000000003`에 직접 접속한다. | 2와 같은 404 화면이 나온다. "예약 가능한 회차가 없습니다" 같은 빈 상태 화면은 없다. | |

#### BT-02 · 클래스 상세 안내 (R-53, R-54)

| 절차 | B 기대 결과 | A 기대 결과 |

| 2. 회차 목록을 확인한다. | 4일 후(남은 4)·5일 후(마감)·20시간 후 회차가 한국 시각으로 보인다. 시작한 회차와 취소된 회차는 없다. | |
| 3. 신청 버튼 전 안내를 확인한다. | 신청 버튼 바로 위 회색 안내 상자(마젠타 아이콘)에 운영자가 승인해야 확정된다는 안내와 상태별 취소 기한이 문장마다 블릿(•)을 붙여 줄을 나눠 보인다. 인원 아래에 "최대 4명까지 신청 가능"이 보인다. | |

#### BT-03 · 핵심 예약 신청 (R-10, R-01, R-02)

| 절차 | B 기대 결과 | A 기대 결과 |
|---|---|---|
| 1. A 도자기 4일 후 회차, 인원 2명, 이름 `브라우저테스트`, 전화 `010-1234-5678`을 입력하고 신청한다. | 제출 중에는 버튼이 비활성화되고 처리 중으로 표시된다. 완료 화면으로 이동한다. | 신청이 거부되고 목 데이터 모드 오류가 표시된다. 입력은 유지된다. 이후 절차는 진행하지 않는다. |

| 3. 예약번호를 복사하고 완료 화면을 새로고침한 뒤, 같은 주소를 새 탭에서 연다. | 새로고침해도 같은 예약번호와 신청 내용이 그대로 보인다. 새 탭에서는 예약번호와 접수 안내만 보이고 신청 내용은 없다. 이 번호를 BT-04·BT-10에서 쓴다. | — |
| 4. A 도자기 상세에 다시 들어간다. | 4일 후 회차의 남은 자리가 4에서 2로 줄었다. | — |

#### BT-04 · 예약 조회 (R-30, R-33)

| 절차 | B 기대 결과 | A 기대 결과 |
|---|---|---|
| 1. 완료 화면의 조회 링크로 `/bookings/lookup`에 간다. | 예약번호가 미리 채워져 있다. | BT-03을 진행하지 못했으므로 `BK-DEMO01`·`0001`로 조회한다. |
| 2. 뒷자리 `5678`을 입력해 조회한다. | 입력 폼이 사라지고 결과 화면으로 바뀐다. 승인 대기 상태와 신청자·일시(시작~종료)·장소·인원 2명(예상 비용)·결제 방법·문의처가 차례로 보이고, 신청자 이름·전화번호는 일부가 `*`로 가려져 있다. 취소 가능 여부가 보인다. 승인 대기가 확정이 아니라는 안내가 있다. 주소는 `?code=<예약번호>&view=result`이고 뒷자리는 없다. | 2명 승인 대기 예약이 같은 형식으로 보인다. |
| 3. 브라우저 뒤로 가기를 누른 뒤 앞으로 가기를 누른다. | 뒤로 가기는 입력값이 남은 조회 폼, 앞으로 가기는 같은 결과 화면이다. | |
| 4. 결과 화면을 새로고침한다. | 예약번호가 채워지고 뒷자리는 빈 입력 폼이 보인다. 뒷자리를 다시 입력해 조회하면 결과 화면으로 바뀐다. | |
| 5. 결과 화면 제목 옆의 "클래스 상세 보기"를 누른다. | 신청한 클래스 상세(`/classes/<id>`)가 열린다. | |
| 6. 브라우저 뒤로 가기를 누른다. | 새로고침과 같이 예약번호가 채워지고 뒷자리는 빈 입력 폼이 보인다. | |
| 7. 뒷자리를 다시 입력해 조회한 뒤 결과 화면 맨 위의 "클래스 목록"을 누른다. | 클래스 목록(`/`)으로 이동한다. 결과 화면에 "다른 예약 조회" 버튼은 없다. | |
| 8. 다시 조회해 결과 화면 배치를 360px·1280px에서 본다. | 안내 상자에 파란 굵은 글씨의 직접 취소 기한(뒤 괄호에 "회차 시작 전" 또는 "시작 24시간 전"), 회색 글씨의 상태 안내가 차례로 있다. 클래스 소개와 준비물은 없다. 예약 취소·다시 조회는 안내 상자 아래 줄에 있다. "클래스 상세 보기"는 제목 오른쪽(좁으면 제목 아래), "다시 조회"는 상세 아래 줄 오른쪽 끝의 연한 파란 버튼이고 "예약 취소"는 같은 줄 왼쪽 끝이다. 가로 스크롤이 없다. | |
