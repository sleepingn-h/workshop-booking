# Architecture Decision Records

## 철학
핵심 흐름에 집중하고, 규칙은 정확하게.

- **범위**: 예약 신청 → 운영자 승인 → 고객 조회 → 고객 취소 → 자리 복구까지, 예약 규칙이 실제로 작동하는 흐름을 고객·운영자 양쪽에서 끝까지 완성하고, 운영자가 클래스·회차를 직접 관리할 수 있게 한다. 결제·알림·고객 계정처럼 이 흐름에 필요하지 않은 기능은 두지 않는다.
- **정확성**: 정원·상태 전이·취소 기한처럼 규칙이 깨질 수 있는 곳에는 확실한 수단을 쓴다. 규칙은 테스트를 먼저 작성한 순수 함수로, 저장 시점의 보장은 DB 트랜잭션과 행 잠금으로 확인한다.
- **단순함**: 그 밖의 구조·의존성·인프라는 가장 단순한 것을 고른다. 모든 계층·파일·의존성은 존재 이유를 설명할 수 있어야 하며, 쓰이지 않거나 이유를 설명할 수 없는 것은 두지 않는다.

---

### ADR-001: Next.js App Router
**결정**: Next.js App Router 하나로 고객 화면, 운영자 화면, REST API를 함께 만든다. 공개 클래스 목록과 신청 폼을 포함한 상세는 검색 노출 대상으로 두고 신청 완료·예약 조회·운영자 페이지는 `noindex`로 제외한다.
**이유**: 클래스 목록·상세의 서버 렌더링(검색 노출·공유 미리보기)과 API(Route Handlers)를 별도 백엔드 없이 한 프로젝트·한 배포로 처리할 수 있다.
**트레이드오프**: 프론트와 백엔드가 같은 배포 단위에 묶인다. 서버·클라이언트 컴포넌트 경계를 직접 관리해야 한다.

### ADR-002: 규칙은 순수 함수, 처리 순서는 db.ts
**결정**: 브라우저는 자체 REST API만 호출한다. 예약 규칙은 `src/lib/rules.ts`의 순수 함수로 두고, 요청 하나의 처리 순서(조회 → 규칙 확인 → 저장)는 `src/lib/db.ts` 함수에 둔다. Route Handler와 서버 컴포넌트는 모두 `db.ts`를 직접 호출한다. 별도 Service·Repository 계층은 두지 않는다. 서버 컴포넌트가 렌더링하는 클래스 목록·상세는 조회 전용 REST API를 두지 않는다.
**이유**: 규칙이 DB와 분리되어 있어 계층을 더 만들지 않아도 테스트할 수 있다. 파일 두 개로 역할이 충분히 나뉘고, 서버 렌더링에서 불필요한 HTTP 왕복과 배포 주소 의존을 없앤다. 호출하는 화면이 없는 API는 코드와 테스트만 늘리므로 만들지 않는다.
**트레이드오프**: 저장소를 교체하려면 `db.ts`를 고쳐야 한다. `db.ts`에 처리 순서와 DB 호출이 함께 있어 이 파일이 커질 수 있다. 외부 클라이언트(앱 등)가 클래스 정보를 조회하려면 API를 새로 추가해야 한다.

### ADR-003: Supabase + schema.sql 하나로 정원 보장
**결정**: 저장소는 Supabase(Postgres)를, 클래스 이미지는 Supabase Storage를 사용한다. 테이블, 예약·관리 함수, 이미지 버킷, 샘플 데이터를 `supabase/schema.sql` 하나에 둔다. 예약 함수는 한 트랜잭션에서 회차 행을 `FOR UPDATE`로 잠그고 확인과 저장을 함께 처리한다.
**이유**: 직접 DB 서버를 운영하지 않고 무료 플랜으로 배포할 수 있으며, 이미지 저장소도 같은 서비스에서 해결된다. supabase-js는 트랜잭션을 지원하지 않으므로, 마지막 자리 동시 신청에서 정원 초과를 막으려면(R-15) DB 함수가 필요하다. 파일 하나로 저장소만 보고 DB를 다시 만들 수 있다.
**트레이드오프**: 핵심 규칙 일부가 SQL에도 들어가 TypeScript와 두 곳에서 관리된다. Supabase CLI·마이그레이션 이력 없이 SQL Editor에서 수동 실행한다.

### ADR-004: 구현 파일마다 테스트, 실제 DB는 시연으로 확인
**결정**: `scripts/hooks/tdd-guard.sh`로 테스트 파일이 없는 구현 파일 편집을 막는다. 규칙(`src/lib/rules.ts`)은 순수 함수 테스트로, `db.ts`·`api.ts`·Route Handler·컴포넌트·`src/proxy.ts`는 Supabase·`fetch`·`db.ts`를 모킹한 테스트로 검증한다(Vitest, React Testing Library). 메모리 저장소나 로컬·테스트용 DB는 두지 않는다(개발용 읽기 전용 목 데이터는 ADR-012). Postgres 함수를 거치는 흐름은 배포 환경 시연으로 확인한다.
**이유**: 테스트 먼저 작성하는 순서를 문서가 아닌 도구로 강제한다. 정원·상태 전이·취소 기한은 DB 없이 빠르게 검증하고, 요청 시각 전달·에러 코드 변환·화면 상태 처리도 인프라 없이 확인할 수 있다.
**트레이드오프**: 구현 파일 수만큼 테스트 파일이 생겨 테스트 작성 시간이 늘어난다. 모킹 테스트는 SQL 함수의 동작을 증명하지 않아 중복 신청·자리 복구·동시 신청 보장(R-15)은 SQL 구현과 시연으로 확인한다. TS 규칙과 SQL 함수가 어긋나도 자동으로 발견되지 않는다.

### ADR-005: 현재 시각은 인자로 전달
**결정**: 규칙 함수는 현재 시각을 인자(`now`)로 받는다. `src/lib/db.ts`가 요청마다 한 번 읽은 요청 시각을 규칙 함수와 Postgres 함수(`p_now`)에 함께 넘기며, Postgres 함수는 `now()`를 쓰지 않는다. 판정 기준은 ARCHITECTURE.md의 "요청 시각"을 따른다.
**이유**: 시작 시각 정각, 확정 예약 24시간 전 정각 같은 시간 경계를 고정 시각 테스트로 그대로 재현할 수 있다. 별도 Clock 객체 없이 함수 인자만으로 해결된다.
**트레이드오프**: 시각의 출처가 DB가 아닌 앱 서버가 된다. 서버 시계 오차는 MVP에서 고려하지 않는다.

### ADR-006: 운영자 인증은 HMAC 서명 쿠키
**결정**: 환경 변수 비밀번호(`ADMIN_PASSWORD`)로 로그인하고, 만료 시각을 `ADMIN_SESSION_SECRET`으로 서명한 httpOnly 쿠키(12시간)를 발급한다. 서버 세션 저장소와 사용자 테이블은 두지 않는다.
**이유**: 운영자가 한 명인 MVP에 인증 서비스나 사용자 관리는 과하다. DB 없이 `src/proxy.ts`(Next.js 16, Node.js 런타임)와 Route Handler에서 같은 함수로 검증할 수 있다.
**트레이드오프**: 운영자 계정을 여러 개 두거나 권한을 나눌 수 없다. 발급한 쿠키를 개별로 무효화할 수 없어, 강제 로그아웃은 서명 키를 바꾸는 방법뿐이다.

### ADR-007: 클라이언트 서버 상태는 TanStack Query
**결정**: 예약 조회·운영자 화면은 TanStack Query의 `useQuery`, 신청·승인·거절·취소와 관리 변경은 `useMutation`으로 처리하고 변경 성공 시 관련 쿼리를 무효화한다. 신청 폼의 회차·남은 자리는 서버 상세에서 받아 `router.refresh()`로 갱신한다. 갱신 흐름은 ARCHITECTURE.md의 "상태 관리"를 따른다.
**이유**: 로딩·빈 결과·실패·재시도와 제출 중 상태를 화면마다 직접 구현하지 않고 일관되게 처리할 수 있다. 클라이언트 쿼리와 서버 상세의 갱신 경로를 분명히 구분한다.
**트레이드오프**: 외부 의존성이 하나 늘어난다. 서버 상세와 클라이언트 쿼리는 각각 갱신해야 한다. 실시간 동기화는 하지 않아 다른 사용자의 변경은 다시 조회할 때 반영된다.

### ADR-008: 수동 승인, 승인 대기도 자리를 차지
**결정**: 신청하면 승인 대기 상태가 되고 운영자가 회차 시작 전까지 승인·거절한다. 승인 대기 예약도 신청 인원만큼 자리를 차지하며 자동 만료는 없다.
**이유**: 결제 없이 운영자가 신청을 확인하는 공방 운영 방식에 맞다. 승인 시점에 정원이 초과되는 경우가 생기지 않아 승인은 상태만 바꾸면 된다.
**트레이드오프**: 운영자가 처리하지 않은 예약이 다른 고객의 신청을 막는다. 시작 후 남은 승인 대기 건은 운영자가 직접 정리해야 한다.

### ADR-009: 회원가입 없이 예약번호 + 전화번호 뒷자리로 조회
**결정**: 고객 계정을 만들지 않는다. 예약번호와 전화번호 뒷자리 4자리가 모두 일치할 때만 조회·취소할 수 있고, 틀린 값이 무엇인지 구분하지 않는다. 조회 결과의 신청자 이름·전화번호는 서버에서 일부를 가려 응답한다. 신청 완료 화면은 주소의 예약번호와 접수 안내만 보여준다.
**이유**: 한 번 예약하는 고객에게 회원가입은 진입 장벽이고 MVP 범위를 크게 늘린다.
**트레이드오프**: 예약번호를 잃어버리면 고객 스스로 찾을 수 없어 공방에 문의해야 한다. 내 예약 목록 같은 기능을 제공할 수 없다.

### ADR-010: 데모 초기화는 schema.sql 재실행
**결정**: 샘플 데이터는 `schema.sql` 끝에 두고, 파일 전체를 SQL Editor에서 다시 실행해 데모를 초기화한다. 샘플 회차 시각은 실행 시점 기준(`now() + interval`)으로 계산한다. 정기 자동 초기화나 서버 시작·조회 시 시각 보정은 하지 않는다.
**이유**: 별도 스크립트·런타임·스케줄러 없이 파일 하나로 준비와 초기화를 해결한다. 예약 데이터를 사용자 모르게 바꾸는 동작을 만들지 않는다.
**트레이드오프**: 초기화하면 테이블·함수와 시연 중 생성한 예약·클래스까지 모두 다시 만든다. 업로드한 Storage 파일은 SQL로 지우지 않아 남는다. 시간이 지나면 시연 회차가 이미 시작했거나 방문자 조작으로 데이터가 달라질 수 있어, 시연 전에 직접 실행해야 하며 README에 이를 안내한다.

### ADR-011: 이미지 업로드는 운영자 API 경유
**결정**: 운영자 화면은 이미지를 자체 API(`PUT /api/admin/classes/:id/image`)로 보내고, Route Handler가 형식·크기를 확인한 뒤 서버 키로 Supabase Storage 공개 버킷에 저장한다. 브라우저에서 Storage로 직접 올리지 않는다.
**이유**: 브라우저는 자체 REST API만 호출한다는 규칙과 운영자 인증을 그대로 쓸 수 있고, 서버 전용 키를 브라우저에 노출하거나 Storage 정책을 따로 만들 필요가 없다.
**트레이드오프**: 파일이 앱 서버를 거쳐 서버 대역폭을 쓰고, 배포 플랫폼의 요청 크기 제한(Vercel 4.5MB) 때문에 이미지를 4MB 이하로 제한한다.

### ADR-012: 개발용 읽기 전용 목 데이터 모드
**결정**: `MOCK_DB=1`이고 production이 아닐 때만 `src/lib/mock-db.ts`의 고정 샘플(Supabase 샘플과 같은 클래스·회차·예약)로 조회 함수를 대신한다. 변경 요청은 `MOCK_READ_ONLY`(503)로 거부한다. Supabase 환경 변수가 비어 있다는 이유로 자동으로 켜지지 않는다.
**이유**: Supabase 프로젝트 없이도 로컬에서 고객·운영자 화면과 상태별 표시를 확인할 수 있다. 조회만 대신하므로 예약 저장의 원본은 계속 Postgres 하나이고, 남은 자리·취소 가능 여부는 같은 `rules.ts`로 계산한다. 명시적 플래그와 production 차단으로 배포 환경에서 가짜 데이터가 노출되지 않는다.
**트레이드오프**: 샘플 데이터가 `schema.sql`과 `mock-db.ts` 두 곳에 있어 함께 고쳐야 한다. 목 모드에서는 신청·승인·관리 흐름을 확인할 수 없고, 조회 결과가 SQL 뷰·함수와 어긋나도 자동으로 발견되지 않는다.
